# PID-GRPO 代码与参数审查（2026-10-25）

## 结论与边界

当前代码具备单 GPU PID 调节 KL 的 GRPO 训练闭环：optimizer update 后评测，
raw guard 先检查，再将 EMA 能力送入 PID，更新 loss 实际读取的 `trainer.beta`，
并保存模型、优化器、调度器、随机状态与控制状态，支持训练内回滚重试。
这能支持工程试验，但尚不能认定其能稳定保护通用能力或优于固定 KL。

此次仅新增本报告与 `configs/pilot_pid_kl.yaml`，没有修改算法、奖励、评测或既有配置。
候选配置默认关闭训练，表示待校准的参数起点，不表示已找到最优超参数。

当前终端的 `python` 是 Conda Python 3.12.9；`python3` 则是系统 Python 3.10。
用 `python -m pytest -q` 得到 **52 passed, 1 skipped**；跳过的是整个
`tests/test_trl_integration.py` 模块，因此其中 3 个 TRL 集成用例此次均未执行。
Conda 环境有 torch 2.7.0+cu126、Transformers 4.53.2、Datasets 2.2.1，
缺少 TRL、PEFT、Accelerate，CUDA 不可用；与项目锁定训练环境不符。
此次没有执行真实模型训练、真实 loss 数值测试或真实恢复测试。
轻量依赖的备用安装仅写入 `/tmp/pid_grpo_audit_deps`，未变更项目训练依赖。

工作区 `data/` 中没有四路 JSONL，只有 `.gitkeep` 和历史 smoke manifest；
配置实际指向另一台环境的 `/root/autodl-tmp/GRPO`，本次未验证该路径的数据与模型。
历史报告引用的 `outputs/` 原始产物在当前工作区缺失，不能独立复核其训练曲线。

## 实现核对

- `src/trainers/real_grpo.py` 构造真实 TRL `GRPOTrainer` 与 LoRA。
- `src/trainers/hf_control_callback.py` 在 `on_step_end` 触发控制，区分梯度累积与 update。
- `src/trainers/pid_grpo_trainer.py` 的适配器更新 `trainer.beta`，并同步配置镜像。
- `src/controllers/pid_controller.py` 使用有符号误差、条件积分、平滑微分、风险门控和乘性更新。
- raw Hard/Invalid 不进入 PID；末步强制评测；当前代码已分别导出 last/best 模型。
- 自动续训只支持 PID 模式，其他模式触发 Hard 后恢复并停止；不应将它们混作同预算恢复对照。

对照 [TRL 0.15.2 官方源码](https://github.com/huggingface/trl/blob/v0.15.2/trl/trainer/grpo_trainer.py)：
loss 确实乘 `self.beta`，组内 reward 按标准差归一化，按回答长度先做样本内平均。
该版 loss 是单次更新的策略梯度形式，没有多轮 PPO clipped surrogate；
不能直接向 YAML 添加新版 `epsilon_high`、`loss_type` 或 `scale_rewards` 并假设生效。
该版也仍计算 reference log-prob，即使 beta=0；文档中来自新版实现的生命周期描述
不能直接当作该锁定版本的事实。项目对 PID 要求正 beta 是明确的自身约束。

## 主要问题及其影响

### 1. 高优先级：能力反馈与实际约束不等价

目标是保持通用能力，但当前 evaluator 只提供生成答案的数学 exact match。
smoke 的四路数据全是 GSM8K，ID 互斥不能使其成为通用能力评测。
任意问答若使用同一“最后一个数字”解析，还会扭曲非数学评分。

此外，beta 惩罚的是训练提示分布上的 reference KL，不是 control 能力损失本身。
“增大 beta 会提升 control 能力”并无单调保证；它也可能只抑制进一步变化，无法修复已遗忘能力。
[PID-Lagrangian 论文](https://arxiv.org/abs/2007.03964) 的约束乘子结论不能直接转移到这个代理执行量。
因此更准确的研究定位是“能力反馈驱动的自适应 KL”，其有效性必须实测。

待审批：引入知识、常识、语言理解等异域 control 与各自 scorer，记录分项，
以成对基线差值、置信区间和逐次监测协议定义控制信号；先测 beta 对能力的局部响应。
若实测 beta 无法控制该指标，再讨论 replay/蒸馏或显式能力约束损失，不能先保证 PID 会解决。

### 2. 高优先级：reward 与 control 共用有误判风险的答案解析

`src/rewards/math_reward.py` 对未匹配到简单 boxed/hash 的文本取最后一个数字。
直接调用当前代码可复现 `is_correct('1/2', '2') == True`，
以及 `is_correct(r'\boxed{\frac{1}{2}}', '2') == True`。
嵌套 LaTeX、分数、单位、多个数字均需专门处理；截断推理中的末尾数字也可能被当作最终答案。
同一错误会同时污染训练奖励和控制反馈，不只是最终报表的问题。

待审批：显式最终答案提取、嵌套括号解析与数学 verifier；区分解析失败和真正答错，
并记录 EOS/截断率。冻结 verifier 后重测初始基线，不能沿用旧分数。

### 3. 高优先级：当前闭环过快释放 KL，积分作用很弱

当前真实配置继承 `Kp=.2, Ki=.05, Kd=.2, beta_min=.001, release=.25`。
以基线 0.6、最大相对下降 5% 为例，Safe=.585、Warn=.576、Hard=.570。
保持输入分数恒为 0.6，直接调用当前控制器得到：

| 控制评测次数 | beta |
| --- | ---: |
| 1 | 0.030000 |
| 5 | 0.009492 |
| 10 | 0.002253 |
| 13 | 0.001000 |

控制器高于 Warn 时主动释放 KL，与当前设计一致，不能称为代码意外。
但能力不变也会很快走到下界，而 `base_beta` 没有作为普通安全释放的下界使用。
对每 50 步测一次、总共 1000 步的运行，13 次评测意味着约第 650 步就降至最低。
若只缩短 K 而保持 25% 释放，释放到下界的训练步数还会更少。

当前 `Ki * integral_max = .05 * .1 = .005`，未计 risk gate 前，
I 最多使 beta 每次额外乘约 1.005；归一化误差只要超过 .1，就能一次填满积分上限。
因此现设置的 I 接近弱小的饱和偏置，难以体现持续偏差累积。

参数层面：放慢释放、提高 beta 下界、扩大积分范围并降低 Ki，见候选配置。
待审批的公式改动：保持下降趋势时禁止释放、以 raw/保守预测辅助 EMA 制动，
以及回滚后按被恢复 beta 明确加压。当前 recovery floor 参考失败 beta，
当失败前 beta 已低于旧 checkpoint beta 时，恢复后可能只保持旧 beta，而非真正增强。

### 4. 高优先级：小间隔、测量分辨率与 EMA 延迟冲突

当前真实设置下 Warn–Hard = `0.2 * .05 * g0 = .01*g0`。
g0=.6 时只有 .006，即 0.6 个百分点；1000 题也仅相当于 6 道题的差距。
单个二项准确率的粗略 95% 半宽约为 `1.96*sqrt(.6*.4/1000)=.0304`，
远大于该间隔。这只是总体推断的示例，不能代替同题成对差值的方差分析。
同一模型的固定贪心测评主要受有限样本代表性和逐题决策翻转影响，不能把每次评测当作独立抽样。

EMA alpha=.4 的低频等效延迟约 `(1-alpha)/alpha=1.5` 次评测，
即 K=50 时约 75 个 update，另有两次测量之间的等待和模型响应延迟。
例：先在 .6 建立 EMA，此后 raw 恒为 .571（仍高于 Hard），
EMA 要到第 4 次下降观测才低于 Warn。Hard guard 仍然只在评测点执行。

参数层面：候选 K=10、alpha=.6，并将 Warn 提前到相对下降 3%。
4096 题仅作为更高分辨率的试验门槛；g0=.6 时半宽仍约 .015，
不能声称因此满足 5% 退化约束的统计功效。正式样本量应由成对翻转率、
容忍误差、多次查看次数决定。反复监测需要预注册逐次检验或其他明确协议。
EMA 不能消除有限样本偏差，较大 deadband 也不能替代置信分析。

### 5. 中优先级：每步一道题，零优势组多，生成预算不足

TRL 0.15.2 中 batch size 是重复后的回答条数。
当前 batch=4、G=4、梯度累积=1，单 GPU 每 update 只有 1 道不同题、4 个回答。
二元奖励全相同则组内 advantage 为零，只剩 KL 梯度。
在回答独立同分布且单次成功率为 p 的简化假设下，该事件概率为 `p^G+(1-p)^G`：
p=.1 时，G=4 为 65.62%，G=8 为 43.05%，G=16 为 18.53%。
真实回答存在相关性，不能把此估算当作实测比率。

参数层面：候选 batch=8、G=8、累积=4，每 update 4 道题、32 个回答。
这也使每 10 步约覆盖 40 个题组，与旧设置每 50 步的 50 个题组接近。
比较实验必须统一这一配置及采样预算，不能把增大 batch 的收益算在 PID 上。
候选完成长度 1024，训练/评测一致；观察截断比例后再决定是否提高到 2048。
对 DeepSeek-R1-Distill 等长思考模型应单独做长度试验，不能直接套此 Qwen-0.5B 配置。

待审批：动态采样、截断样本处理、token 级/固定分母 loss 与 reward scaling 消融。
[DAPO](https://arxiv.org/abs/2503.14476) 讨论了零优势组、长度和截断问题；
[Dr. GRPO](https://arxiv.org/abs/2503.20783) 分析了 GRPO 的优化偏差。
这些支持做消融，不证明它们一定改善本项目。不要直接移除 KL：那会改变本研究的执行量。

### 6. 中优先级：复现与对照协议仍需完善

- `.gitignore` 中未锚定的 `data/` 会忽略 `src/data/`。当前文件存在，
  但 `git ls-files src` 不包含 `dataset_builder.py` 与该目录的 `__init__.py`。
  当前工作区能导入，干净 clone 会缺少训练入口依赖。建议修正忽略规则并纳入源码。
- 目前只检查样本 ID，缺少内容哈希、近重复与来源级泄漏检查。
- `report_to=[]`；控制 CSV 虽定义 measured_kl 列，却没有在 callback 中填入。
  训练信息主要在 Trainer 日志/安全 checkpoint 内，缺少统一可分析的 reward/KL/长度/分项曲线。
- best model 只要求高于 Hard，回滚候选要求不低于 Warn。二者是不同可行性口径，需预注册。
- 初始化 checkpoint 没有 domain validation 分数，因此选模不会选中未训练基线；
  最终仅评测 best，缺少同预算 last 的独立最终结果，可能掩盖后期退化。
- 文档声称超时保护，但 evaluator/guard 中没有实际 deadline；挂起时不会自动返回 Invalid。
- `docs/test_report.md` 的旧单侧 PID 公式和参数已过时，不能用于解释当前有符号 PID。

以上实现/协议变更此次均未修改，待与算法相关改动一起明确审批范围。

## 候选参数与校准方法

候选文件：`configs/pilot_pid_kl.yaml`，继承真实配置，模型仍为固定 revision 的
Qwen2.5-0.5B-Instruct，不自动切换到历史 smoke 使用的 1.5B 模型。

| 参数 | 当前真实配置 | 候选起点 | 目的 |
| --- | ---: | ---: | --- |
| LR / 初始 beta | 1e-6 / .04 | 保留 | 先不同时改变优化速度与约束强度 |
| G / batch / 累积 | 4 / 4 / 1 | 8 / 8 / 4 | 增加题目覆盖与有效组概率 |
| 完成长度 / 评测长度 | 256 / 128 | 1024 / 1024 | 减少推理截断与协议不一致 |
| LoRA dropout | .05 | 0 | 减少生成与训练前向的 dropout 差异 |
| temperature | .9 | 1 | 与该版 loss 未缩放 log-prob 保持更一致 |
| K / EMA alpha | 50 / .4 | 10 / .6 | 缩短反馈延迟 |
| Kp / Ki / Kd | .2 / .05 / .2 | .15 / .02 / .1 | 减弱短期噪声与微分放大 |
| 积分上限 / 安全保留 | .1 / .5 | 2 / .8 | 让持续偏差具有可见积分作用 |
| beta 下界 / 上界 | .001 / 1 | .01 / .3 | 避免过早接近无 KL 或过强约束 |
| 单次上调上限 / 释放比例 | 2 / .25 | 1.5 / .05 | 降低倍率跳变，缓慢释放 |
| deadband | 0 | .1 | 归一化尺度上的初步死区，须按数据重算 |
| Safe/Warn 退化预算比例 | .5 / .8 | .4 / .6 | 在相同 Hard 底线下提前干预 |
| pilot / control 最少题数 | 1000 步 / 1000 题 | 200 步 / 4096 题 | 先校准，题数不是充分性保证 |

[DeepSeekMath](https://arxiv.org/html/2402.03300v3#S4.SS2) 使用 LR=1e-6、
beta=.04、G=64、最大长度1024；这是保留 LR/beta 的文献参照，
不表示其 7B 大批量全参结果可迁移到此处 0.5B LoRA。
这里的 PID 增益、G=8、beta 边界与阈值比例均是工程先验，没有论文证明其最优。
温度=1也不保证严格 on-policy：实际 generation config 的 top-k/top-p 仍需在锁定运行时核对。

建议校准顺序：

1. 先审批并修正 scorer/control 与复现问题，冻结四路数据、模型和评测协议，重测 g0。
2. 相同数据顺序、批量和生成预算下，短跑固定 beta={.01,.04,.10}，
   观察异域能力、domain 收益、实测 KL、零优势组比例、截断率及耗时。
   如果都无明显能力变化，先延长试验或换任务；无需强行让 PID 触发。
3. 保留 PID 候选及 P-only、PI 对照，逐项启用 I/D；
   Kp 可试 {.1,.15,.3}，Ki={0,.02}，Kd={0,.1}，按响应与噪声选窄范围，
   不进行高成本全网格。控制周期和累积批量改变后必须重新标定。
4. 不依赖 final test 调参。冻结后对 no-KL、固定 KL、PID 使用至少 3 个配对种子，
   最终确认可扩至 5 个；统一生成 token、更新预算与真实耗时记录。
   回滚重算的 token/update 也计成本，不能只比较回滚后的 global_step。
   同预算 last 为主结果，best 为选模附加结果，均报告域内和异域独立测试及成对区间。

当前只建议期待更平稳、可解释的控制曲线与更高有效梯度比例，不能给出准确率提升预测。
正式比较应回答：在相同能力退化约束与计算预算下，PID 的任务收益是否优于经过调参的固定 KL。
若固定 beta 在所有试验中都足够安全，PID 没有明显收益也属于有效结论。
